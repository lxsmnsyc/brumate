# Debate: no hand-written client scripts

## Settled structure

In ship order:

1. **Default `scripts` in dev** (P1, O5). When the caller passes no `scripts`, `virtual:brumate/routes` supplies `/@vite/client` plus the loader of the generated start module, the same pair the preview page builds (vite.ts:1665). The tags go into the tail of the first chunk (runtime/server.ts:3367), so streaming does not change. An explicit `scripts`, including `''`, still wins. The `/@id/__x00__` start URL becomes one shared constant.
2. **Default `scripts` in production** (P2, P9, O1, O6). The SSR build reads the client manifest in `buildStart`, as it already reads the build ID and hints, and bakes the entry tag into the routes module (prerender.ts:109 builds the same tag). A missing client manifest or entry is a build error, not a warning. A build-ID mismatch reuses the skew warning. The manifest path comes from the resolved client `outDir`, so Nitro's output works.
3. **`vite dev` serves pages** (A2, P6, P7, P11, O8, O9, O11). `configureServer` returns a post middleware that calls `handle` through the SSR environment for every method and pipes the stream. It calls `next()` only when `handle` returns undefined. It is skipped under `middlewareMode` (own servers) and when `server.environments.nitro` exists. The plugin sets `appType: 'custom'` when the user left it unset. With a user-set `spa` or `mpa` the middleware is skipped and a one-time warning names the fix. Render errors answer with `errorPage` and `ssrFixStacktrace`.
4. **Nitro** (P4). The entry drops the `?assets=client` import and the `import.meta.env.DEV` ternary. One e2e on examples/nitro covers dev and build.
5. **Cleanup** (P5, P8, O3). Delete the hand-written tags (J3) and, in five Node examples, `server.ts`, `node.ts` and the dev half of `server.prod.ts`. The `dev` script becomes `vite`. todos keeps a `middlewareMode` server as the own-server case. Ship `toRequest` and `send` as `brumate/node`, since production servers still need them. Add a test that fails when `@vite/client` appears in examples, website/docs or benchmarks, excluding benchmarks/brumate-0.3 (pinned to 0.3.0) and the doc of the `scripts` override.

After steps 1 and 2, own servers and Nitro write no tag. Step 3 removes `server.ts` for plain `vite dev`.

## Budget

- device: one worker, no parallel worktrees: 8 GB RAM, 3.2 GB free, CPU-bound (J1)
- time: 6 to 10 days for one worker. Two comparable plugin features each landed in one commit (O10). Repointing the example e2e tests is the main cost (P8, P10).
- tokens: about 200k for the build. Each step loads vite.ts, about 30k tokens (J9, P10).

## Rejected

- `clientScripts(vite?)` helper that every server calls: apps still write the call, which misses "never" (A1)
- Plugin owns the client entry, with `src/client.ts` optional: `src/client.ts` is an import line, not a script tag, and Nitro's config names it as input (P3, beaten by O2)
- Tags and production entry only, without `vite dev` serving pages: plain `vite dev` serves no route page today (J4), so the goal's plain-vite-dev clause would stay empty (O7)
- "Nitro's dev worker cannot see the plugin's dev or build mode": the routes module is generated by the plugin's load hook in the Vite process (O4)

## Proofs

None. Every question was settled by reading the source.

## Prior art

- idlip (https://github.com/lxsmnsyc/idlip/blob/8248e3f447759eb162cfa7584d40c6aacac7fa53/packages/idlip/src/vite/plugin.ts#L329-L355): the plugin serves pages in `vite dev` and `transformIndexHtml` adds the client tag. It buffers the whole page, and its production entry still writes the loader tag by hand (J5).
- SvelteKit (accf16ca32): the plugin serves pages in dev, takes `client.start` from the manifest, and adds `/@vite/client` itself (J6). It sets `appType: 'custom'` (J11).
- Astro (c302892e4a) adds `/@vite/client` to every dev page. @marko/run (8960d94604) serves dev pages from its adapter (J7).

## Open risks

- Under a root `_error.brm`, `handle` never returns undefined, so unknown paths such as `/favicon.ico` render the 404 page in dev. This matches today's hand-written servers. Accepted.
- Nitro's client `outDir` (`.output/public`) versus the manifest path step 2 reads: covered by the Nitro e2e of step 4. Measured in that step.

## Inferred choices

- `vite dev` serving pages is in scope, because the goal names plain `vite dev` and it serves no pages today (A2 ruling, J4).
- Breaking `handle()` options and the example layout need no deprecation period (J8, from GOAL.md constraints).
- Targets the next minor, because release/0.9 has only its release node left (J8).
- `brumate/node` is in scope, because production servers still need `toRequest`/`send` once `server.ts` goes (P8 ruling).
