# Debate: Brumate apps never write the /@vite/client tag or the client entry script by hand, in dev or production, whether they run plain vite dev, Nitro, or their own server

## Settled structure

- P1: Step 1 (dev), the core: when the caller passes no `scripts`, the generated virtual:brumate/routes module supplies a default. In dev it is the /@vite/client tag plus the loader tag for '/@id/__x00__virtual:brumate/start', exactly the pair the preview page already builds (vite.ts:1665); the tags are written once into firstRender's `tail` (server.ts:3367), after the first render and before </body>, as `async` module scripts, so streaming is unchanged: nothing is buffered and later #loading/#defer chunks still follow the tags. An explicit `scripts` string (including '') still wins, so custom servers and CSP nonce setups keep control. Fixes the plain-vite-dev and own-server dev cases in 6 examples, 3 docs pages, 2 benchmarks, website/scripts/dev.ts. (1 day, size S, one file in plugin + tests)
- P2: Step 2 (production): the SSR build bakes the client entry URL into the routes module, so `server.route(request)` needs no `scripts`. buildStart of the SSR build already reads the client output for the build ID (.brumate/build.json) and the client hints (vite.ts:2270-2290), so reading `.vite/manifest.json` there for the client input and emitting `<script type=module async src=BASE+file>` is the same mechanism; prerender.ts:109 already builds this exact tag from the manifest entry. This deletes the manifest read, entry lookup and tag from every server.prod.ts (about 5 of 59-84 lines each) and the earlyHints stays an option. Streaming: the tag is the same async tail script as in P1. (2 days, size S-M (build-order edge cases, base path, manifest:true auto-set))
- P4: Step 4: Nitro and other hosts. Under Nitro the entry file stops importing `?assets=client` and writing the DEV ternary (entry-server.ts:11-14); it is just `handle(request, {address})`. The default of P1/P2 is chosen by the plugin's isServe/isSsrBuild, not by import.meta.env, so it holds in Nitro's dev worker (Vite serves /@vite/client and the start module on the same dev origin) and its build. The open risk is where Nitro writes the client build (.output/public) versus where P2 looks; P2 should take the manifest path from the resolved client environment outDir, not a fixed dist/client. Needs one e2e on examples/nitro in dev and build. (1.5 days, size M (e2e of nitro dev+build, 1 worker given J1 recommends 1))
- P5: Step 5, last: delete the hand-written tags and test the rule. Remove `scripts:` from the 6 server.ts, 6 server.prod.ts, examples/nitro, website/scripts/dev.ts, benchmarks/brumate(-0.3), and the snippets in getting-started.md:110 and deploying.md:33 (the doc then explains only that `scripts` overrides the default). Add a test that fails if '@vite/client' appears in examples/, website/docs or benchmarks outside the plugin, which enforces the goal. Breaking handle() options need no deprecation period. (0.5 day, size S, mostly deletions; tokens: edits touch about 5 kB per example)
- A2: Larger variant for the same goal: the plugin serves pages in vite dev itself (a post-middleware in configureServer that calls the routes module's handle with the default scripts), as SvelteKit does at exports/vite/dev/index.js:315, Astro in vite-plugin-app and idlip in plugin.ts:329-355. Plain `vite dev` then needs no server.ts at all, not only no tags. Costs: the error page, Node-to-Request conversion (node.ts in each example) and server-function POST routing move into the plugin, the HMR/ssrLoadModule path must keep working with Nitro (which owns dev), and it adds roughly a medium node on top of P1. Worth it only if the goal widens to 'no server.ts'; P1 is a prerequisite either way. (4 days, size M-L)
- P6: Step 3 (replaces rejected P3; A2 folded in): configureServer returns a post-middleware that answers GET/HEAD page requests in vite dev by importing virtual:brumate/routes through the SSR environment, calling handle(Request) (default scripts from P1), and piping the web ReadableStream to the Node response, so streaming is kept (idlip buffers; brumate does not). It falls through with next() when handle returns undefined, so Vite's own files, /@vite/client and the RPC POSTs of vite.ts:2759 are untouched. (a) Own server: skip when `server.config.server.middlewareMode` is true, which is exactly the setup of every example server.ts (createServer({server:{middlewareMode:true}, appType:'custom'})); an app that wants its own handler therefore never gets a second answer, and an option `pages: false` turns the middleware off in normal mode. A post-middleware also runs only after the app's own pre-middleware had a chance to end the response. (b) Nitro: skip when `server.environments.nitro` exists, which Nitro's dev plugin reads at _build/vite.dev.mjs:76 and creates itself; Nitro's worker then renders with the P1 default, since the routes module is generated in the Vite process (O4 ruled). Both checks are plain config reads at configureServer time, no request-time guess. (3 days, size M (middleware, Node to Request conversion, three modes e2e))
- P7: Error pages in the dev middleware reuse what exists: a throw from the routes module or handle is caught and answered 500 text/html with errorPage(error, server) (dev-error.ts, already used by the preview page at vite.ts:1688 and exported as brumate/vite errorPage), so Vite's overlay and the devtools show compile errors as in the 6 hand servers. Rendering errors that handle itself turns into a 500 page stay the app's business. The same try/catch also calls server.ssrFixStacktrace(error). No new error UI. (0.5 day, included in P6 if done together; size S)
- P8: Examples and node helper. After P6, plain `vite dev` runs every example, so server.ts, node.ts and the dev half of server.prod.ts are deleted in 5 of the 6 Node examples (package.json dev script becomes `vite`); one example, todos, keeps a middlewareMode server.ts as the documented own-server case and the e2e of P6(a). node.ts is byte-identical in the examples I compared (cmp: browser-async, hackernews, kit-app, ui match todos), plus 33-line server.ts and 59-84 line server.prod.ts per J2, so shipping `toRequest` and `send` as `brumate/node` is in scope: P6 needs the same conversion inside the plugin anyway, so exporting it costs about 0.5 day and removes 5 copies; it is optional and goes last, and it does not decide the goal. A production server generator (a `node dist/server` entry) stays out of scope: server.prod.ts shrinks to the manifest-free handle call plus static files, about 35 lines. Risk: e2e and tests that spawn server.ts must be repointed to `vite`. (1.5 days, size S-M (6 examples, scripts, e2e specs))
- P9: Amends P2 with O1 and O6. The SSR build reads the client manifest in buildStart and a missing manifest or missing client entry is an error (this.error), not the warning the build-ID check gives today; the client-first order already holds under Nitro's single `vite build` (J10) and under the two chained commands of the plain examples, and the error text says to build the client first. The baked entry carries the client build ID it read: when BRUMATE_BUILD or the build ID found by the existing readBuildId (vite.ts:2281) differs from the one in the manifest read, the existing skew warning is reused, no new check. P1's dev URL '/@id/__x00__virtual:brumate/start' becomes one exported constant used by the preview page (vite.ts:1665) and the routes default (O5). (2.5 days, size M (was 2, plus error path, build-ID reuse, constant))
- P10: Ship order and total. 1) P1 default dev scripts plus shared constant (1 day). 2) P9 production default with error on missing manifest (2.5). 3) P6+P7 dev middleware, depends on 1 (3.5). 4) P4 Nitro e2e in dev and build, needs 1 and 2 (1.5). 5) P8 delete example glue, doc snippets, optional brumate/node, last (1.5). Total about 10 days of one worker, because J1 recommends 1 parallel worktree (CPU bound, 8 GB RAM); steps 1-2 are the 'never write a tag' result for own servers and Nitro (3.5 days), step 3 adds plain vite dev. Tokens: every step loads vite.ts (about 30k tokens, J9), so about 5 x 40k = 200k tokens. P5's guard test excludes benchmarks/brumate-0.3 (pins brumate 0.3.0, O3) and allows the docs sentence that explains the `scripts` override. P3 and A1 are dropped, as ruled. (10 days, one worker; about 200k tokens)
- P11: Amends P6 with O8, O9, O11. The plugin sets `appType: 'custom'` in its config hook when the user left appType unset (as SvelteKit does, J11), so Vite's SPA html fallback never rewrites req.url to /index.html before the post-middleware and the routes see the real URL; the plugin never overrides an appType the user set. A user who set 'spa' or 'mpa' gets no pages middleware and a one-time dev warning that brumate pages need appType 'custom' (the same middlewareMode skip as P6(a), so no double answer). The middleware answers every method and every Accept: it calls handle(Request) and falls through with next() only when handle returns undefined, so POST server function calls, endpoints, fetch() requests and non-HTML routes reach the routes module and Vite's own files, /@vite/client and RPC still fall through. P6's other parts (Nitro skip via server.environments.nitro, errorPage, streaming pipe) stay. (0.5 day added to P6, size S; P10 total read as 6-10 days, e2e repointing of the examples is the main cost)
