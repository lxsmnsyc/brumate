# Debate: Remove default values from the brumate context API, as Solid does, so createContext takes only a key and $getContext throws when no provider above set the context

## Settled structure

- P1: Core change, one node: createContext takes only a key and Context has only key. $getContext throws a named error that carries the context key when no provider above set it, on the server and in the browser. Delete the defaultValue fallbacks (server.ts:805, client/context.ts:62,129,237), the CONTEXT_ADDED hook and the madeContexts and waitingReads maps. routeContext and navigationContext lose their defaults because the runtime already provides both to every page. (1 M node, about 400 lines touched, net negative)
- P2: Optional reads get one explicit, local primitive: a compile-time $hasContext(Context) that returns whether a provider above set it. Contexts are static since #469, so the answer is fixed when the scope is made and keeps the graph static. A part that works with no provider writes `$hasContext(C) ? $getContext(C) : fallback`, and the fallback is built per reader, so it is never module-global and cannot cross requests (J5). It mirrors the `has` of Svelte 5's createContext triplet. (1 compiler fn plus runtime check, S-M)
- P3: Ship order after P1 and P2: (a) the 50 `store(null)` defaults in packages/ui/src, where the part already tests `state` for null, become $hasContext checks; (b) the 7 `null`/`false` defaults and the 2 `noInput` defaults. Both are mechanical per site: delete the default argument, replace the read. 61 createContext sites and 76 $getContext calls in ui. One node per batch so each reviews alone. (2 M nodes, about 61 sites and 76 calls)
- P4: Landing: build it inside the context-stores story, as a node before store-repair-compare, on feat/context-stores, so the CONTEXT_ADDED, madeContexts and waitingReads code the story added never reaches next. store-repair-compare then no longer restores an en-US LocaleContext default store: LocaleContext reads optionally with $hasContext and falls back to en-US per reader. This removes the one remaining planned default and keeps one story PR to next. (0 extra PRs to next; one story PR as planned)
- P5: Last node: tests, docs and release text. Update the 24 packages/brumate test calls, 12 website/docs calls and 4 examples/tracker calls, rewrite the default section of website/docs/context.md, change decisions.md, add a test that a missing provider throws with the key in the message, and write the changeset as a minor bump. (1 S-M node)
- P6: Premise check to record: Solid 1.x has optional defaults and returns undefined with none, and Solid 2.0 keeps an optional default too, but createContext<T>() with none makes useContext throw ContextNotFoundError, and it recommends an explicit null context for optional reads. So brumate going further (no default argument at all) is stricter than Solid and relies on P2 for the optional case, as Svelte does.
- P9: $hasContext is a compile-time `$` function exported from brumate/signals beside $getContext, and is added to the list at decisions.md:7. Call: `$hasContext(Context)` returns a boolean. Server: it runs the same walk up the scope parents that $getContext uses, and returns true when a node above holds the key or the key is ROUTE_KEY. Browser: it calls findProvider on the page state (J11), so no new resume data and no new flag. Providers are static (#469), so the answer is fixed when the scope is made and never changes while the page lives. (1 part of the M node N2, about 60 lines)
- P11: Node split, replacing the 2 M nodes of P3 and the S-M node of P5 (O3 asks for realistic sizing). N1 core throw and deletions (P1): M. N2 $hasContext plus the optional flag of $getContext and $store, with BRM codes, server and client resume tests (P9, P10): M. N3 ui batch a, the 50 store(null) readers and the tests that render a part alone, using `$store(C, true)` or `$getContext(C, true)`: M, maybe split by file group if review fixes pile up. N4 ui batch b, the 7 null/false defaults, 2 noInput, the 24 packages/brumate test calls and the Locale reader: M. N5 docs, 4 examples, decisions.md, changeset: S. Total 4 M plus 1 S, with N2 gating N3 and N4, and N1 independent of N2 so it can run first. (5 nodes: 4 M and 1 S)
- P12: Placement against the story: the nodes sit inside the context-stores story, N1 and N2 first, then N3 and N4, all before store-repair-compare. store-repair-compare's LocaleContext en-US default store item is replaced by N4: the Locale reader uses `$getContext(LocaleContext, true)` and falls back to en-US per reader, so no module-global store is restored. The rest of store-repair-compare (the object-memo store test) stays. The story PR to next waits for N5, which is the cost of the user's choice to follow Svelte. (5 added nodes before the story PR; store-repair-compare loses one item)
- P13: Answer to O5: the src deletion is small (about 5 sites), so the argument for P1 is correctness, not size: the leak of J1 and J5 goes away and the story's CONTEXT_ADDED, madeContexts and waitingReads code is not shipped. Tests that mount a part alone get a provider or the optional form in N4. Page roots keep $route and $navigation because the runtime provides both (J8); a non-page root in a test provides them or does not read them. (5 src sites changed in N1)
- O9: Use $hasContext alone and narrow $store to a guarded form: the compiler accepts `const x = $hasContext(C) ? $store(C) : undefined` (and the same with `$store(g.state)` where g is `$hasContext(C) ? $getContext(C) : undefined`) as one recognised shape. The guard is the user's own primitive, the branch is a compile-time fact (P9, static providers), and no flag, no second return type and no `?.` rule are added. N2 shrinks to $hasContext plus one pattern check in the $store analysis, and readers keep one idiom. (0 new call-signature arguments (P10 adds 2))

## Rejected

- P7: Cheaper variant with no new compiler function: optional reads take a per-call fallback, `$getContext(C, () => fallback)`. The thunk runs per reader, so it is local and not module-global, but createContext and the throw (P1) stay as proposed. Saves the $hasContext function but the 61 sites each carry a thunk, and the compiler must check the thunk for static reads. Solid 2.0's own advice (a null default) is not usable here, since the null object is the module-global value the goal removes.. Why not: Q1: the user chose the Svelte shape with $hasContext over a fallback at the read.
- P8: Cheapest variant: keep the default argument but make it a factory, createContext(key, () => value), run per reader, and ban store defaults by type. Needs no ui migration of reads, but keeps defaultValue paths, CONTEXT_ADDED machinery and the stale idea of a context with a hidden value, so it does not reach the goal of key-only createContext. Listed as the floor to beat.. Why not: Keeps CONTEXT_ADDED (J4) and module-global factories are still allowed to return shared objects; it does not reach a key-only API.
- O6: Cheaper way to the stated motivation (no module-global leaked state): keep a default argument but forbid object and store defaults at the type level and in a compiler check, allowing only primitives (null, false, a string). Primitives cannot leak state. Then only the 50 store(null) sites and the noInput objects change, createContext(key, default) stays, and the CONTEXT_ADDED link code is deleted since store defaults are gone. It misses 'key only', so it is a fallback if O1 and O2 hold.. Why not: Q1: the user chose key-only contexts as in Svelte; primitive defaults stay out.
- P10: Answer to O1, exact optional form: a second argument, the literal `true`, on $getContext and on $store. `$getContext(C, true)` returns undefined when no provider is above. `$store(source, true)` takes the same sources as today (a context, or a key of a $getContext value, BRM194 otherwise) and gives undefined when the provider is missing. Ui readers write `const g = $getContext(C, true); const x = $store(g?.state, true)` or `const x = $store(C, true)`; the compiler accepts `g?.state` only when g came from `$getContext(C, true)`. The variable x is undefined without a provider, and the optional form allows only const, so a new BRM error covers `let` and no write reaches a missing store. Server: the read finds no value and records no store link in the page state. Browser: findStore finds no provider on resume (J11), so linkRead and waitingReads are not used and x stays undefined. The compiler checks the literal, so the graph stays static.. Why not: O8: a second optional-read form beyond the user's Svelte choice (Q1); O9 reaches the same readers with $hasContext alone. (by O8, O9)
