# Debate: Decide how a brumate handler or $client callback that reads an async memo with no value yet behaves, so reads stay sound without breaking common patterns or growing the client much

## Settled structure

- P3: During a reload the handler does not wait: the slot holds the old value (J2), so it reads the last settled value, as Solid 2.0 reads after a first value (J12) and React/Svelte keep old UI during updates (J10, J14). The runtime tells the two apart by the slot value itself (a promise in a memo slot means no value yet), so the forms.md:395 $optimistic sample compiles and keeps every guess during reloads (fixes J7), and the wait costs nothing on a page whose memos have arrived.
- P4: Reads the list cannot see (a function prop called from a child, an imported helper given an accessor, the browser render of `await $memo` from J5) throw a NotReady-carrying error into the nearest #try, never return the promise. The check keys on the slot value being a loading memo promise (loadingValues, but filled only for memo slots, fixing #352 finding 1 on promise props and signals) and on the read being outside a memo compute or effect, not on a handling counter, so reads after an await in an async handler are caught too (fixes J8's first gap). Effects keep #352's skip-and-rerun, and also rerun once on rejection so the error reaches #try.
- P6: Client size about +170 to +200 B gzip over main on todos, about the same as #352's +164 B (J9): the wait helper in handle() is about 50 B gzip and replaces #352's handler() counter wrap (about 30 B); loadingValues and the effect skip stay; each handler that reads a memo adds a short slot array (about 8-15 B raw) to module metadata. Shipping: rework PR #352 itself for 0.4.0 (rework-same-pr): drop the BRM182 error (the code can stay as a note-free list builder), add the list and wait, mark only memo slots loading, drop the handling counter, update async-data.md and decisions.md:27. The 0.5.0 browser-await spike (J5) later removes the browser-render source of no-value reads. (185 B gzip todos JS before load, over main)
  - amended by P14: Client size rises from P6's ~185 B to about 260-300 B gzip on todos. Sketches of P1+P4+P9+P10+P11 measure +292 B appended to the core chunk. That overstates a little, since the sketches share no names with the core, and leaves out the per-handler slot lists and memo-slot marking. Dropping the load-time rejection of every pending promise (a further +59 B) keeps O7 bounded through P10 alone. Shipping is unchanged: rework PR #352 for 0.4.0.
- O8: Cheaper in runtime and with no page-wide hold: P8's throw before the first value (Solid 2, J12; P4 with O1's update exemption) as the default, plus `await name` of a memo inside a handler, which the compiler already accepts as syntax for renders (decisions.md:27), lowered to wait for that slot's first value. An async handler's promise does not hold lastHandler (handlers.ts:237-240 wraps the value), so only that handler waits. Qwik, the resumable framework closest to J15, makes handlers `await resource.value` the same way. About +5-20 B gzip for the wait helper over P4, plus the lowering in codegen; a fast click without `await` still goes to #try (Q1). (61 B gzip runtime (P4 + wait helper sketch))
  - amended by O14: Drop O8. Keep its finding that an async handler's promise does not hold lastHandler (handlers.ts:237-240), which O10 relies on.
- P11: Amends P4 with O1's exemption. A counter wraps the update queue and the browser render (components.ts render), and get() does not throw while it is set. Cost: +29 B gzip in the cumulative sketch, plus a try/finally on every queued update pass (one increment and one decrement per pass, not per read).
- P12: Settles O4/J16. Promise props and streamed promise signals are async values, as main already treats them (props.ts:57-60, resume.ts:224-233) and as decisions.md:26 decides. resume keeps marking every streamed promise slot loading, as #352's resume.ts:230 does. A promise that code writes into a signal later stays a plain value. #352's async-data.md:131 line is replaced with that rule. This costs metadata per handler (more slots per list) and no runtime bytes.

## Rejected

- P1: Before the first value, a handler or $client callback waits: handle() adds one more promise to the Promise.all it already awaits before the shared chain (handlers.ts:226-229), resolving when every memo slot on the handler's wait list holds a value (or its error). The body then runs synchronously in one pass with settled values, so no read sees a promise and no #352 handling counter is needed. Order and preventDefault are kept (J3, J4); this is React 18's replay of a discrete event after its boundary's data arrives (J11).. Why not:  (by O2, O6)
- P2: The compiler emits the wait list per handler as page-module metadata beside the existing `w` list (state.ts:20, read in updateReady at updates.ts:491, already awaited inside handle(), so no extra load): the own-scope slots of every memo the handler or the same-script functions it calls read, of any kind, not only async-memo, minus reads guarded by $isPending (the guard is an opt-out meaning 'run now'). Listing every memo, not only provably async ones, closes J8's miss of imported 'use server' memos at no analysis cost; pending-reads.ts's walk and isGuarded are reused to collect slots instead of reporting BRM182.. Why not:  (by O4)
- P5: A memo that rejects releases the wait and the handler's read throws the memo error into #try, as on main (decisions.md:128). A streamed memo always settles or rejects by the end of the server stream, so the wait is bounded by the stream; a browser-rendered memo waits as long as its server call. Because waits sit before the shared chain, later events queue behind a waiting one (as they already do behind loading code); DEV warns in devtools when a handler has waited over 5 s, at 0 production bytes.. Why not:  (by O2, O7)
- P7: Cheaper on client-size and time: no compiler list. handle() waits for every loading memo slot in the handler's scope and its parents (scope.p chain), the boundary granularity React 18 uses (J11); pending-reads.ts and BRM182 are deleted (-215 lines), function props from ancestors are covered, and the runtime adds about 40 B gzip. Cost: a slow memo in a layout that only a #loading body reads holds every click under that layout until it streams.. Why not: Over-waits by the proponent's own account, and with O2 a slow layout memo would hold every click on the page. (by O2, O5)
- P8: Cheapest in time for 0.4.0: keep #352's throw design (Solid-style, J12) with three fixes: mark only memo slots loading, skip BRM182 for memos that markup reads outside #loading on server-rendered components (the server waited, so they have a value; fixes the forms.md sample), and document the after-await gap. Handlers fail into #try instead of waiting, so a fast click during streaming shows an error, the trade the wait design avoids.. Why not: The maintainer chose the ideal behavior over delivery time (Q1, Q2); an error on a quick click while the page streams is the outcome the goal tries to avoid. Its memo-slot fix is kept in P4.
- O3: Keep P1's wait but cap it: race the slot promises with the document's load event and a timer (length to be chosen, Q3). This bounds the page-wide hold of O2 and the cut-stream case of O7, and costs about +24 B gzip over P1 (P1+P4+cap sketch +162 B against +123 B without the cap).. Why not: 
- P9: Scope of the hold (amends P1, answers O2): loading code stays on the one page-wide chain as on main, but a data wait does not. An input and the submit of the same form share the form's lane, and so do two handlers of one component, so their order holds. Handlers of other forms and components keep running. Why not: O10: lanes break the order between components that main keeps (a form's submit writes a DialogTrigger's signal, dialog.md:101), and with the Q3 cap one bounded chain keeps every order for 38 B less. - P10: Bound (Q3; amends P5, answers O3, O6, O7). Each slot's wait races a cap, after which the handler runs and an unready read throws into #catch through P4. Size: +55 B over P9, +24 B more for the guess reset.

- A load the browser starts (a browser-rendered memo, a promise prop, rpc) waits at most 5 s.
