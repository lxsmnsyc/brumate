# Debate: Decide how a #loading boundary in the browser treats a memo that loads again: a $fresh memo primitive, a new boundary block, an opt-in on #loading, or today's stale content

## Settled structure

- P1: Option C: `#loading (memo) {...} #else {...}` re-arms on the client. When a memo named in `on` loads again, the boundary hides its body (kept alive like #offscreen, so state and DOM survive) and shows the #else body; when the value arrives it swaps back. Without `on`, behavior is today's stale content. Names the dependency like Solid 2's `on`, so no new keyword and the grammar already parses it (J5). Q1 rules out $isPending in the body, so the boundary itself must do this. (0.5 kB gzip client, only in apps using `on`)
- P2: Ship step 1, from main as its own PR: make the server honor `#loading (expr)`. Today codegen ignores LoadingBlock.on and silently drops the boundary and fallback (J5). Either read `on` (server already streams, so `on` can mean: the first render waits on those memos, same as no header) or have the analyzer error until step 2 lands. Needs: one codegen branch in markup.ts emitLoading (~1840) or a check.ts diagnostic. (1 small PR, ~1 session, ~15k tokens)
- P3: Ship step 2: client runtime for re-arm. (a) Compiler ships the #else body to the client only for a #loading with `on`, as #try ships #catch only when it reads a memo (J3), gated by a features.ts flag so other apps pay 0 bytes (J7). (b) A small `loadingBoundary(scope, anchor, memos, render, kind)` reuses blockStart/rangeEnd/hiding from offscreen and the pending() check in updates.ts:407; the NotReady throw already exists (J6). (c) Estimate: errors.ts is 2.7 kB raw for a comparable fallback mechanism, offscreen is part of branches.ts 12.6 kB, so the new code is about 1 kB raw. (0.5 kB gzip, 0 for apps without `on`)
- P4: Ship step 3: docs and dev guard. Update website/docs/async-data.md:77 (replace the $isPending advice with `on`), add a decisions.md entry, and a DEV warning like Solid's LOADING_ON_OUTSIDE_HOLD when a read of the same memo outside the boundary makes the fallback unreachable. Tests: client test that a second load shows #else then restores the same DOM nodes and input state. (1 docs+tests PR, ~20k tokens)
- P8: Why a fresh-UI feature beats stale (answers P7, O7, Q3). Stale is wrong, not ugly, when the body is a function of the key that changed. (1) A search or detail view: `user = $memo(load(id))`; after the id changes, the body keeps showing the old user's name, avatar and form fields while the new one loads, and a click on 'Delete' or a submit inside it acts on the wrong record. Dimming with $isPending (O7) does not stop the click or the typing into a stale input. (2) Pagination or filter tables: the old rows sit under a new page number or filter chip, so the page states something false. (3) Prices, balances, permissions: a stale 'admin' panel after the user switches account is a security-flavored mistake. Dimming covers only cases where stale is a correct, merely old, picture (a feed refreshing); that is a large share but not these. The opt-in costs 0 bytes to apps that do not use it (J7), and Solid 2, Vue and React all give the fallback-on-update option, so users of those expect it. (3 concrete cases where stale content misleads or lets a user act on the wrong record)
- P9: Revised P3, a concrete runtime against O1, O2, O4. Compiler: a `#loading (m...)` always emits markers on the server (<!--l-->, <!--/l-->, and the #else body in a template) even when settled, only for blocks with a header (answers O1; blocks without a header keep J13 output). Client: `loadingOn(scope, anchor, slots, render, kind)` runs as an effect on the pending() of each slot in `on`, not a NotReady catcher (answers O2). State bit in the marker data as in offscreen (`start.data` 0 body, 1 fallback, -1 not settled): the effect does nothing until pending() has been false once, so a streaming value never arms it (answers O4). On pending true it hides the body with the `hiding` holder and renders #else once; on false it removes #else and shows the body again; a newer load before the first finishes changes nothing, because pending stays true. (0.6 kB gzip, basis: offscreen+hiding reuse leaves one effect, one state bit and one render call, about 1.5 kB raw like catchInto (errors.ts is 2.7 kB raw for 1 function with module loading); gzip ratio about 0.35-0.4; plus per-boundary HTML of two comments)
- P10: O5 verdict: adopt the lowering idea for the runtime, not as source rewriting. Checked decisions.md:103-105: bodies of #offscreen and #if are numbered after a block ID, and #loading bodies are numbered after the boundary ID (5.0). If the compiler wrapped the body A in a synthetic #offscreen, the scope IDs inside A would shift against the server render unless the server output wraps the same way, and the server has no #offscreen for a streamed body. So the compiler would have to lower on both sides, and I did not run it. The safe form is P9: the boundary itself is the owner of body A (its scope kind is already the boundary's child) and calls the existing hiding holder directly, so no ID is added. I did not test hiding on a scope that streams in a template; that is the one open check, and a test in P4 covers it (second load after a streamed first load). (0 kB beyond P9 if hiding is reused directly)
- P11: Delay (Q2): show #else at once by default, and add no delay in v1. Prior art: React throttles only the reveal of a fallback (300 ms, FALLBACK_THROTTLE_MS) so that a stream of fallbacks does not flicker, and it avoids the fallback entirely for transitions; Vue <Suspense> has a `timeout` prop whose default shows the fallback only after the timeout, but only on pending updates, and it is an explicit prop; Solid 2 shows the fallback at once when `on` re-arms and offers no default delay; Svelte shows pending at once. Every library has a way to hold the fallback, none hides it by default for fast loads. Because brumate keeps the body alive behind the fallback (hidden, not destroyed), a flash costs a layout flip, not state loss, so the cost of a flash is lower than in React. Decision: no default delay; if wanted later, add a second header argument (`#loading (m, 200)`) as a non-breaking opt-in, which is 0 bytes until used. (0 kB in v1; about 0.1 kB gzip if a timer is added later)
- P12: Re-estimate and order: step 1 (P2, bug fix from main) about 15k tokens; step 2 (P9) about 0.6 kB gzip only in apps that use a header, 0 otherwise, plus two marker comments per header block (about 20 bytes of HTML); step 3 docs and tests (P4 without the DEV warning, per O3) about 13k tokens. Against client budgets (13.9 kB todos, 23.6 kB dashboard, J8), 0.6 kB is 2.5-4.3 percent for the apps that opt in. The #else body ships to the client only for blocks with a header (J3). (0.6 kB gzip for opt-in apps; 0 for others)

## Rejected

- P5: Option A, `$fresh(memo)`: a memo primitive whose read throws NotReady to the nearest #loading while it reloads. Cheaper to describe (no grammar change) but the choice sits in the script, far from the markup that shows it, and the same memo cannot be stale in one place and fresh in another without two declarations. Needs the same client boundary code as P1 (nothing catches NotReady at a boundary today, J6) plus a new compiled primitive, so it is P1's runtime cost plus a new $-primitive and server semantics for a function that has no meaning on the server.. Why not: O6: reads outside markup have nothing to catch NotReady; and the choice sits in the script, not where the fallback is written. (by O6)
- P6: Option B, a new boundary block (for example #refresh or #reload): cheapest to reason about per block, but adds a keyword to a language that already has #loading with a dead `on` header, so it makes two blocks with overlapping jobs and a second fallback syntax. Decisions rule syntax proposals against new # blocks that are not markup; this is markup, but P1 reaches the same result with zero new syntax.. Why not: Same runtime as P1 plus a new keyword beside an existing, unused #loading header (J5); no gain on any axis.
- P7: Option D, keep stale content and add nothing: 0 bytes, 0 tokens. The cost is that Q1 rules out the only documented way (#if $isPending inside the body), so users have no sanctioned way to show loading on update. Cheapest on all three axes, fails the goal; only the P2 bug fix would remain.. Why not: O13 concedes that dimming fails bodies with editable controls (P8 case 1); Q3 sets fresh UI as the point.
- O5: Compile `#loading (m) {A} #else {B}` on the client to existing parts: `#offscreen (!$isPending(m)) {A}` plus `#if ($isPending(m)) {B}`. Hide, keep-alive, ID numbering after the block, and $isPending reads already exist, so the new runtime is 0 kB beyond the #else body. Q1 rules out users writing $isPending in the body; it does not rule out the compiler lowering to it. Needs the O4 first-settle guard and the O1 marker, but both are compiler output, not a new runtime function.. Why not: P10: a synthetic #offscreen wrapper shifts scope IDs against the server render (decisions.md:103-105); calling hiding directly keeps the idea without the wrapper.

## Open risks

- O10 (time): P10 leaves open that hiding works on a body that streamed in. offscreen hides by finding the body in scope.children with k === kind, and the streamed body is rendered in the boundary's own ID space, so I found no code that links it as a child of the component scope. If it is not linked, hide() finds no body and the re-arm silently does nothing after a streamed first load, the common case. Not tested by either side; a 20-line client test would settle it.. Open because: J14 makes it less likely: streamed body scopes carry their parent and resume links them into parent.children. Whether hiding's kind match finds them is untested; a client test in step 2 settles it.

## Answers from the user

- Q1 (judge): Is #if ($isPending(x)) inside a #loading body an acceptable way to show loading on updates? Answer: No. $isPending is meant for shifting styles and similar; #if($isPending(...)) inside a loading boundary is a broken design.
- Q2 (proponent): Should a re-armed #loading hold back a flash of the fallback for fast reloads (a delay such as 200 ms before showing #else), or show it at once? Answer: The user asks what the optimal choice is. The debate must decide it with evidence.
- Q3 (judge): When a #loading body's data loads again in the browser, is styling the old content (dimming, a spinner via $isPending) enough, or must the boundary be able to swap to its #else fallback? Answer: That is the point of the debate: decide whether #loading should have a feature that shows only fresh UI and not the stale UI that memos keep. The debate must argue it, not the user.
