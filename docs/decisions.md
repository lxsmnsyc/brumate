# Decisions

## Decided

- Components run on the server only. The client resumes and never runs a component function again to rebuild state.
- The reactive graph is built at compile time. The runtime does not record subscriptions.
- There are twelve compile-time functions: `$props`, `$signal`, `$memo`, `$effect`, `$client`, `$untrack`, `$produce`, `$isPending`, `$setContext`, `$getContext`, `$id` and `$title`.
- `$id()` makes an ID from the scope's ID and the call's position, so server and client agree without counting at runtime.
- `ref=$bind(name)` writes an element into a `$signal`, or into a `Bindable` `let` prop, which forwards it to the caller. There is no separate ref function. `ref` always takes `$bind`, on elements, dynamic tags and components, so a component forwards a ref as it forwards any bound prop. A bare `ref=name` is a compile error, with no deprecation period. The server never sends an element: the state holds an element reference, which the browser resolves.
- `$signal` does not track the values in its initial value.
- `$effect` never runs on page load. It keeps Solid's name, but not its timing. `$client` is the way to run code without a change.
- Signals never leave the file. Imported code receives values.
- Server functions use the `'use server'` directive, on a function or on a file.
- Server functions may capture module-scope bindings and imports only.
- There is no `'use client'` directive.
- There is no `#static` block. Markup is static by default, so marking it changes nothing. `brumate inspect` reports what ships and why instead.
- Scripts, expressions and attribute values cannot contain markup. `#for` and `#template` are used instead.
- Props are live only if a parent passes them values that can change. The project analysis finds these props. A file compiled alone treats every prop as live.
- The client code of a component is split into an entry, one part per client root, an update part and a shared part.
- Scope instances link to their parent with `p`, so client code reads outer values by walking up.
- Lists keep the raw item of each item scope in the state, so keys can be computed again on the client.
- The Vite plugin finds every `.brm` file under the root, so the manifest and the server registry list all components.
- A change to a `.brm` file reloads the page instead of replacing modules.
- A component rendered on the client comes from its render module, a third output next to the server and client modules.
- `#loading` streams out of order: the fallback first, then the body in a `<template>` with its scopes and an inline swap script.
- Any `$memo` can hold a promise, as in Solid, Compostate and Atemno. Reading a value that is still loading throws a not-ready error that carries the load, and nothing turns a memo into a promise. On the server, a memo computes when it is first read. A memo that read a loading value does not keep the error, so it computes again when read after the load. Markup outside every `#loading` body waits there, and a `#loading` body waits in its own stream chunk. On the client, a memo that reads a loading value keeps its old value and is pending until the value arrives.
- `await` says where the server waits instead of streaming. `const name = await $memo(value)` waits where the memo is declared, and `await name` of a memo waits in the render around the read: the page outside every `#loading` body, the body around a `#loading` block, or the request for a `#defer` body. A run of `await $memo` declarations loads at the same time. In the browser the value is settled, so both are plain reads. Code that the browser renders can await only a memo, which the compiler checks, and a component whose script awaits a promise renders on the server only. A `#loading` body whose values are ready when the block renders, and that renders nothing that can wait on its own, renders in place in the ID space of its boundary.
- `$isPending(memo)` is true while a memo loads on the client, and false on the server.
- Routes are files under `src/routes`. A layout wraps its folder, and `@name` folders are sibling routes that render in the `name` slot of the layout for the same URL. Layouts render before their children, so their contexts reach the routes. The loader loads pages with `fetch` once it runs, and streams them in as they arrive. The code for it loads on the first navigation. A link keeps the layouts that stay the same, with their state, and replaces only the routes that change.
- seroval does not write or read regular expressions, in the page state or in server function calls. A pattern from a client could take the server a long time to match. Error stacks are not written either.
- Server function calls and form posts from a page of another site answer 403. The check reads `Origin`, or `Sec-Fetch-Site` without it, so forms need no token.
- `$action(fn)` holds the result of a form. Without scripts the page renders again with it, and with the loader it is written into the page. `refresh(fn)` in a server function loads again the memos that call `fn`, which the compiler finds.
- A form posts to a server function with `action=fn`, without client code. The server answers with a 303 back to the page, so the page renders again with the new data.
- The project is named brumate, and its files use `.brm`. Brumation is how reptiles stay dormant in the cold and resume when it warms, as a page resumes on its first event without hydrating.
- Compile-time functions such as `$signal` are imported from `brumate/signals`, not global. The compiler finds them through the import, so a renamed import works and their types reach only the files that import them. The compiler removes the import.
- Server rendering streams only. `renderToStream` sends the whole first render at once, closing tags included, and streams what resolves later after it, as Solid does. `render` returns the parts for custom servers. There is no `renderToString`, because waiting for every `#loading` body defeats streaming.
- A component can render the whole document. The runtime adds the doctype, and puts the head before `</head>` and the state, scripts and portals before `</body>`.
- `render` and `renderToStream` take a `nonce` for the inline scripts: the state records and the swap scripts.
- Styles are scoped with a `b-c-<hash>` attribute, under the `b-` prefix that the compiler reserves, so markup and data cannot write it. Style variables are custom properties on the component's top-level elements, and the stylesheet is inlined once per page.
- There is no `$store`. Objects and arrays in signals change by assigning a new value, or with `$produce`, which changes a draft and shares what it does not change. Reads stay per signal, so the graph stays static and nothing extra is resumed. A keyed `#for` compares the old and new lists and updates only the items that changed.
- Server functions read the request with `getEvent()`, and answer with `ServerError` and `redirect`. Other errors reach the browser as a generic message.
- `src/middleware.ts` runs for every request of the app, before the `_middleware.ts` of the folders: pages, endpoints, server function calls, form posts and `#defer` bodies, with `event.kind` and `event.call` to tell them apart. Calls from other sites are refused before it runs. A `'use server'` file can export `middleware` for its own functions. Middleware hands values on through `event.locals`, typed by the `Locals` interface, and `event.waitUntil` keeps work going after the response through the host's `waitUntil` when the server passes one.
- The core makes one Trusted Types policy, `brumate`, where the browser has them, and passes the markup that it inserts and the scripts that it copies through it as they are. A site with `require-trusted-types-for 'script'` allows it with `trusted-types brumate`.
- An error in client code, a handler, an effect, a `$client` callback or a memo that loads, goes to the nearest `#try` around the scope of the code, through the parents and the owners of scopes, which renders its `#catch` body in the browser. A `#try` whose body holds client code ships both bodies and keeps a marker. Without a `#try`, the page gets a `brumate:error` event on `window` and the error is logged. `onError` of the loader sees every error first.
- `$route()` and `$navigation()` are contexts that the runtime provides to the whole page. The server reads the request and the params of the route, and the browser reads `location` and the params from `b-params` of the page state, and updates their readers when navigation changes them. `navigate(href)` from `brumate/routes` asks the loader for the page, and loads it in full without one. The loader sets `data-navigating` on `<html>` while a page loads, announces the new page in a live region of its own, and moves the focus to its first `<h1>` or `<main>`, except when only the query string changes.
- For readers that run no scripts, crawlers by default, the server renders `#loading` and `#defer` bodies in place, in the order of the page, with the same state as when they stream. `inOrder` decides per request.
- `getEvent().signal` aborts when the request's signal does, or when the reader of the response goes away, for pages, calls and `#defer` requests. A page that is left sends no more bodies.
- Environment variables are declared once, in `src/env.ts`, with a Standard Schema for each, split into server and public values. The server checks them when it starts and fails with every missing or wrong one. The browser gets the file without the server schemas and with the values of the public variables written in, so no prefix in a name decides what ships. Only components import the file in code that the browser loads. The compiler reports a read of a server variable in code that runs in the browser, and a value made from one that the page state would send, with imports found by their resolved path. The server refuses a page whose state holds the value of a server variable of 8 characters or more, which catches a helper that reads one.
- `rateLimit({ max, window })` is called first thing in a server function, not wrapped around it, so the compiler needs no new form and the limit reads the event as `getEvent()` does. It counts in a sliding window of two counters per key, in memory by default and in any store with an atomic increment. A request counts first, and the limit decides on the count that the increment returns, so requests at the same time cannot all pass. Refused requests count too, which needs no decrement in the store. The key is explicit: the app's, such as the account of a sign-in or the user, or else the address of the client. The address comes from the server, or from `X-Forwarded-For` when the server saw one of the proxies that the app names, never from a header alone. Without a key or an address, a limit throws in production and does not count in development, rather than count every caller together. Middleware counts each route by its pattern, such as `/api/[id]`. Limits count unless turned off, and never while the build prerenders.
- Skew protection: each build has an ID, which the client build writes to `.brumate/build.json` and the server build reads, or `BRUMATE_BUILD` names for both. The page state carries it, calls and `#defer` requests send it, and a call to a function that is gone answers 409 with the server's build. The browser then loads the next page in full, posts a form again without scripts, and loads a page of another build in full instead of keeping its layouts. Forms carry the ID as `__build` in their URL, and a post without scripts from another build to a function that is gone goes back to its page with 303. When the code of a handler fails to load, the browser asks the server for its build, and loads the page again only when it differs, so a module that throws goes to `#try`. A page loads again, or in full, once for each build in a tab, kept in session storage, so a broken deploy or a cache of old pages cannot loop. The `keep` option keeps the files of earlier builds in the client output.
- `getEvent()` works before the first `await` of a server function, middleware or endpoint, and anywhere in a component while it renders. The runtime sets the event while it starts a call and clears it right after, so it never needs `AsyncLocalStorage`, and never returns the event of another request. Code keeps the event in a variable and passes it to helpers.
- Errors in the page state keep their name and message only.
- Contexts are named by a key that is the same on the server and the client. The page state links each component to the scope that rendered it, records provided values and the slots of readers, so the client finds providers without running code.
- The head is the title and `#head` blocks. `renderToStream` puts it before `</head>`, or passes it to `start`, and `render` returns it. A title or `#head` in a `#loading` body that resolves after the first render streams with the body. A script moves it into the head and sets the title.
- seroval is the serializer. The page state is a stream of seroval cross-reference code records, one inline script each, so promises do not hold up the state. Server function calls use seroval JSON.
  - Each record hands a function of its values to `self.$brm`. The core calls it when it starts, so a page that never gets an event never builds its state.
  - The browser runs the scripts, which is not `eval`. Under a Content Security Policy they need the `nonce` of the render.
  - The code is smaller than the JSON nodes and faster to write. On the `/` page of `examples/todos`, the state is 673 B instead of 1485 B, and the benchmark renders about 1.5 times as many pages per second.
  - The core does not need seroval's reader for the page, so seroval loads with the first server function call. The core is 7.6 KB gzip instead of 15 KB.
  - Records of scopes with the same kind, parent and shape, such as the items of a list, go in one flat array per group. Each item then costs its slots and the gap to the ID before it, instead of an object with `k`, `p`, its slots array and a copy of its item. The core rebuilds the records when it reads the page. In the benchmark, one more todo costs 214 B of HTML instead of 254 B, 26 B gzip instead of 36 B, and 100 todos render about 1.4 times as fast. The core grows by 148 B gzip.
  - A `#for` item whose list is a signal, memo or prop of a scope around it does not write its item. The core sets it from that list by the item's position in its group. An item cannot change on its own: the analyzer rejects a write to a loop variable, and a change in place changes the object that the list holds too. The server checks that each item is the value at its position in the list, and writes the items when one is not, when the list is in an earlier record, or when it is not an array or a Set. Computed lists, such as `todos.filter(…)`, and lists of a value in an item keep their items, because the client would have to compute them again. On the todos benchmark, the state for 100 todos drops from 5.9 kB to 5.2 kB, and one more todo costs 164 B of HTML instead of 172 B.
  - The kind and the parent of an item are not read from the markers in the page. The core reads the state before it has the components' code, and markers carry only the scope ID, so they would need more bytes for the same information.
- Markup marks less when the compiler can show that the core still finds what it needs. In the benchmark, one more todo costs 174 B of HTML instead of 214 B, 20 B gzip instead of 26 B. The core grows by about 80 B gzip, and the loader does not change.
  - A live insert that is the whole content of an element updates the element's children through the element's `b-b`, with no `<!--t…-->` and `<!--/t-->`.
  - A list item whose body is one element is marked by that element's `b-b`, with no `<!--i…-->` and `<!--/i-->`. The element gets an anchor for it if it has none.
  - An element with handlers and no other client code has no `b-b` when an element around it in the same scope has one. Its handlers find their scope with `closest`.
  - The last two apply only to elements that the HTML parser keeps whole. A `<p>` ends at a `<div>` that a child component renders, and a `<table>` moves out content that does not belong in it. The comments, or an anchor of its own, still work then.
  - `b-on` keeps the component ID in each entry. Without it the loader would need the scope's component before the core reads the state, so the module could not load in the same round trip as the core, or every page would need a table of IDs. Leaving it out would save 12 B of HTML per todo, but only about 0.2 B gzip, because the repeated text compresses well.
  - Elements that only an update needs still get their own `b-b`. Finding them by a path from an element around them would save about 3 B gzip per todo, but a path breaks when the parser moves or splits elements.
- Scope IDs are integers given in render order. A render can start above another one with `base`, so several roots and pages that the client loads in place never share IDs.
- A child component keeps its props in its own slots. The parent links to the child's scope to update them.
- The compiler splits client roots and server functions into modules itself. It does not use another splitter. A component whose parts are small in all ships them as one module, because one request costs more than the bytes it saves.
- A component's stylesheet is inlined before its first instance on the page, so a page carries only the CSS of what it renders. There is no CSS file of every component, because it would load CSS that the page does not use and block rendering.
- A dynamic tag is a `#key` block on its tag, so a new element name or component renders again. A component in the page state is written as its ID. The client code that changes the value uses the component's render module.
- Effects run after the other updates of a write, once each, so they see the new markup and every new memo value.
- The type checker reports a signal or memo that the client reads and whose type seroval cannot write, such as a function or a class instance with methods.
- `.brm` files are type-checked through generated TypeScript, with a Volar language plugin. `brumate-tsc` checks a project, and `@brumate/typescript-plugin` serves editors.
- `children` ship as the HTML that the server rendered. When the client inserts them again, it runs the updates of the scopes in them, so the values are current. Updates to markup that is not in the page do nothing.
- Changing a reactive value in place, such as `todos.push(todo)` or `todo.done = true`, is a warning. Nothing updates, because the value is the same. `$produce(todos, (draft) => { draft.push(todo) })` is the way to write it.
- The core is one module whose helpers are exports of their own, and the loader reads only its `loader` export, so a build keeps the helpers that its components call and leaves out the rest. Features that change how the core reads the page, such as the pages that client navigation adds and hot updates, are modules that set hooks of the core when they load, and they read the core with `import()`. The cost is a few bytes in the loader to load them, and a small chunk after the first client navigation. A core per page would need a chunk per set of features, and more requests.
- After `load`, when the browser is idle, the loader preloads the core and the handlers' code of elements in or near the viewport, so a first click needs no request. It costs 97 B gzip in the loader, and the bytes of the core and the modules on every page that has handlers, even when nobody clicks. `prefetch="none"`, Save-Data, 2G connections and the `preload: false` option turn it off.
  - Note, 2026-10-25: the page's code now loads when it starts, in one bundle per root component. `prefetch` and the `preload` option were removed.
- Server functions validate their arguments with helpers of `brumate/server` that take any Standard Schema: `parse`, `safeParse`, `parseForm` and `fieldErrors`. The function calls them in its body.
  - A helper needs no compiler change, and works the same in a component and in a `'use server'` file. The schema and the helper stay on the server, because only the body of the server function reads them.
  - A wrapper, such as `validated(schema, fn)`, would hide the server function from the compiler, which finds server functions by their `'use server'` directive.
  - Validators that the compiler generates from the TypeScript types would need the type checker in every build, and could not express rules such as an email or a minimum.
  - The Standard Schema interface is copied into the package, as its authors ask, so brumate has no dependency for it and works with Zod, Valibot, ArkType and others.
  - `parse` throws a `ServerError` with status 400 and the first issue as the message. The issues are not sent with the error, so the protocol of errors and the client do not change. A function that wants to show field errors uses `safeParse` or `parseForm` and returns the issues as a value.
  - Issues are copied as plain data, a message and a path of strings and numbers, so seroval can send them and fields that a library adds, such as the input, stay on the server.
  - `parseForm` nests dotted names into objects, and makes arrays of repeated names and names that end with `[]`. A part named `__proto__`, `constructor` or `prototype` is an issue, so a form cannot change a prototype.
- `#offscreen (visible) { … }` hides its body and keeps it in the page, as React's `<Activity mode="hidden">` does.
  - A body that is hidden when the page renders is not rendered. The client renders it the first time it shows, as it renders an `#if` body. Hidden content costs nothing until it is needed.
  - The client hides each node at the top level of the body. An element gets an inline `display: none !important`, and a text node gets empty text. The element's own inline `display` comes back when the body shows.
  - The nodes stay in the page. Removing them would reload iframes, stop videos, and lose focus, the selection and the scroll inside them.
  - It is not the `hidden` attribute. A stylesheet such as `.panel { display: flex }` overrides the `[hidden]` rule of the browser, and the body would show. An inline `!important` declaration wins over every stylesheet.
  - Updates of the markup still apply while it is hidden, so it is current when it shows. A changed inline style or text is kept for when it shows, and new nodes at the top level are hidden too.
  - Effects and `$client` callbacks of the body run their cleanups when it hides, and wait while it is hidden. When it shows, the ones that ran before or that would have run run once with the current values. `<window>` and `<document>` listeners in the body do not run while it is hidden.
  - Nothing goes to the server when a body hides or shows.
  - The portals of the body are hidden with it, so a dialog of a hidden tab does not stay on the page.
- `#defer (trigger) { … } #else { … }` renders its body on the server in a later request, when the trigger fires in the browser.
  - The request is the URL of the page and the boundary ID, so nothing comes from the browser that needs signing. The server renders the route again, with the base of the page, and sends only that body.
  - The scopes of `#loading` and `#defer` bodies are numbered after their boundary ID, such as `5.0`, so the second render numbers the page the same way, whatever order the data arrives in.
  - The bodies of `#if`, `#switch`, `#for`, `#repeat`, `#try` and `#offscreen` are numbered after an ID of the block, so the markup after them keeps its IDs when the second render takes another branch, such as for a user who is signed in on a prerendered page.
  - The browser also sends the scope and anchor of the block. When the second render puts the boundary elsewhere, such as after the data changed, the server answers 409 and the fallback stays.
  - A boundary ID names the bodies around it, such as `0.0` inside boundary `0`. The second render renders those bodies, without sending them, so a block can be inside a `#loading` or `#defer` body, also of a parent component.
- The loader listens to each event type once, on the document, and runs the handlers as if each element had its own listener: `:capture` handlers from the outside in, then the others from the target outwards, and an event that does not bubble only on its target. The listener of a type is passive until a handler of the type has `:prevent`, since a handler that loads later cannot prevent anyway, so `:passive` has nothing to do. Browsers make a document listener of `wheel` and `touchmove` passive unless it says otherwise, which made `:prevent` on them do nothing before.
- There is no adapter for compiled messages, such as Paraglide JS. Paraglide works with any framework: a message that the server renders ships no code, a message in client code is an import that the bundler keeps only where it is used, and Paraglide has its own middleware for the locale of a request, reads the locale in the browser itself, and localizes links. A guide comes when the website or an app needs translations. Whether a message in a `#loading` body that streams after the middleware returns keeps the locale is not checked yet.
- There is no taint, as React's `experimental_taintObjectReference`, to stop a value from reaching the page.
  - It is a check, not a guarantee. A copy of a tainted object, such as `{ ...user }`, is not tainted, so it would give a sense of safety that it does not deliver.
  - Any package can call it, also on values it does not own, and fail the renders of an app with errors that the app cannot fix.
  - The page state only holds what client code reads, so a value stays on the server unless the browser needs it. Server code picks the fields it sends.
- Handlers are wrapped by functions of `brumate/events` for what must happen before their code loads: `prevent(handler, ...keys)`, `stop`, `once` and `capture`, as Svelte 5 replaced its modifiers with wrapper functions. The compiler reads the calls in an event attribute and writes them into `b-on`, so the loader applies them on the first event, and the call stays in the client code, where it returns a copy of the handler that carries its modifiers. Keys are `event.key` names that TypeScript checks, with `Space` for the space bar. `b-on` holds them with commas, as `keydown:prevent(ArrowDown,Enter)`, since it separates its entries with spaces. A modifier after the event name, such as `onSubmit:prevent`, works with a warning until a later version, and is a compile error on a component, which gets the handler as a prop.
- `budget.event` measures the first run of a handler: the entry of its component, its own part, the updates that it loads with it, and what they import. The loader and the core are left out, since every page and every first event load them, and `loader` and the core size cover them. A later run of a handler loads nothing, so the first run is the one that a reader waits for.
- `visit` in `brumate/testing` answers the requests of a page in the test, with the route handler and the server function handler of the app, through a `fetch` that follows redirects and keeps cookies. It does not start a server, so a test runs as fast as `mount`, and the server code shares modules with the test.
  - A DOM environment such as happy-dom drops `set-cookie` from the headers that a `Response` is made with, and `cookie` from those of a `Request`. The server adds `set-cookie` after it makes a response, and `visit` sets the request headers after it makes a request, so cookies work in a test.
- `batched` of `brumate/batch` gathers calls only in the browser. The server renders the rows of a list one after another, and a row waits for its data before the next starts, so a batch there would hold one key and add a wait. Rendering rows at the same time would change the order in which scopes get their IDs, which the browser must match. On the server, each call reads its key at once, inside the render, so it reads the event and shares the result of equal calls.
- A memo of a component that the browser renders takes the promise that the render made for its slot, the first time it computes. The render module calls the memo's code to render, so computing it again called each server function twice per row.
- A `<title>` sets the title of the page from `#head`, as `<meta>` and `<link>` go in `#head`, so the head has one rule and the markup stays valid HTML. Elsewhere it is an error, except in an `<svg>` and in a `<head>` element. The element keeps `b-t`, and the core sets `document.title` from the last `title[b-t]` in the page, whenever a block adds or removes one or its text changes, so blocks decide the title without code. When none is left, the title stays. With one title, it is the head's only `<title>`. With several, the server also writes the last one first, for readers without scripts. The core watches the page only once it has such a title. `$title` stays with a warning until a later version.
- Early hints name the loader and the core, with what they import, and no handler parts. The client build writes them to `.brumate/hints.json`, and the routes of the server build read the file, since the two builds can run in separate processes. A page gets them as `<link rel="modulepreload">`, as `Link` headers that hosts turn into `103` responses, and through `earlyHints` for a server that sends a `103` itself before it renders. Client navigation and `#defer` requests get none.
- There is no `use=` or `use:name` syntax for behaviors of an element, as Svelte's actions. A behavior is a function that takes the element, which `ref` and `$client` run, so the syntax would be a second way to write what two lines already do, with its own questions: what runs again when an argument changes, several behaviors on one element, and spreads. The UI components lean on the platform, such as `popover`, `<dialog>` and CSS anchor positioning, so they need few behaviors. What the syntax would add, loading the code when the element comes into view, `$client` does instead: with `'visible'`, a callback that reads an element of its markup through `ref` waits for that element. The syntax can come back if the UI components show that they need it.
- `$debounced(value, ms)` and `$throttled(value, ms)` are memos of `value`. The server renders the value, and the browser computes the memo after its wait, with the values of then, so a burst of changes computes once. The memo is pending while it waits. `ms` is a number literal, because the client code of a memo holds the wait as it is, with no slot of its own.
- There is no `$persisted`. A preference goes in a cookie, which the server reads for the first render, and an `$effect` writes it when it changes, which [Effects](../website/docs/effects.md#values-that-stay-across-visits) shows. That is three lines, and the effect loads with the first change. `localStorage` and `sessionStorage` cannot be read by the server, so a value kept there needs code that runs on load, and the page changes after it shows. A one-line helper for them would make that the easy path, against loading code only when someone interacts.
- A handler in a spread, such as the `onClick` that a component passes on with `{...rest}`, goes into `b-on` as `click=Parent#h1@3`: the client function of the caller, the caller's scope after `@`, and the modifiers of its wrappers. The server knows the function from the reference of the function prop, so only functions that the compiler marked can go through. An element with spreads writes one `b-on` with its own handlers first. Markup that the browser renders gets the attributes of a spread and not its handlers yet, since the browser has the function and no reference.
- The children of a component render where the component inserts them, so they read its contexts, as React's children read the context of the component that renders them. A scope at the top of the children keeps the caller's scope as its parent, since its values are the caller's, and gets `t`, the scope of the insert, which contexts are found from on the server and in the browser. Children that the component does not insert render after it, inside its root scope, so the page state has their HTML for the browser to insert later. In the browser, an insert passes its scope only when it inserts a prop, since only a prop can hold children.
- A `#template` passed as a prop goes to the browser as a reference to an export of the component that wrote it, named `t` and its site, such as `Page#t3`. The export holds the code of the template and reads the values of its component from the scope of the reference. A render cannot wait, so the core calls a template at once: its code starts to load when the page state is read, and an update waits for the templates that are still loading.
- The attributes of an element with spreads are one object, merged in their order, so each name is written once: a later value wins, and the values of `class` all apply. An update of a spread in the browser merges the static attributes of the element the same way.

- A memo whose compute throws, or whose promise rejects, holds the error as its value, and each read of it throws. The error goes to the `#try` around the code that read it, whether an insert, a binding, another memo, an effect or a handler, so a write runs every update and only the readers of the failed memo throw. When the memo computes again without a throw, it holds the value again. A memo that nothing reads keeps its error, with a warning in development. This is how Solid and Compostate treat it, and how a memo already holds a pending promise as its state. The pass has no error rule, so no reader sees the new value of one signal with the old value of a memo that failed. A `#try` ships its `#catch` body to the browser when it reads a memo. On the server the read fails the same way, where the memo is read.
- Hosts are Nitro's: its presets build the app for Node, Bun, Deno, Cloudflare, Vercel and the rest, so brumate has no adapters of its own. Features that need the host, such as a cache store or WebSocket, use Nitro's storage layer and its WebSocket support, and a plain handler for an app that writes its own server.
