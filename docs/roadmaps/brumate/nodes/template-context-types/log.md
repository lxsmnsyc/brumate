# Log: template-context-types

## 2026-10-28

- Probe on main: `<ListBox items=(animals) item=row />` with `#template row(a) { <p>{a.nope}</p> }` in packages/ui. brumate-tsc reports only `TS7006: Parameter 'a' implicitly has an 'any' type` at the parameter. The generated code was `async function row(a)` and `item: (row)`.
- Smallest change: write the template at the use as `item: (async (a): Promise<$$Markup> => { ... })`. The probe then reports `Page.brm(14,9): Property 'nope' does not exist on type 'Animal'`, at the field.
- Which templates: an untyped one whose every read is a value attribute of a component or dynamic tag that passes it as it is (`item=row`, `item=(row)`, `{row}`). Counted over the oxc trees of the scope that declares it. Any other read (a call, an element attribute, `cond ? row : x`, the script) keeps the declaration, since a declaration and inline copies together would report the body's errors twice.
- Shadowing: the generator keeps a stack of the names that each generated block declares (for item and index, repeat index, catch names, block script declarations, declared templates, template parameters). At a use, a name declared between the template's scope and the use that the template also reads (or that equals its name) makes it fall back to the declaration. So does a template that passes itself. The fallback throws, drops the template from the inline set and writes the file again; each pass declares one more template, so it ends.
- Mappings: the body is copied with its mappings at each use. A source offset maps to several generated ranges. brumate-tsc reports a body error once (tsc dedupes identical diagnostics), and a parameter error per use where the type differs: two ListBoxes with `animals` and `cars` report `name` missing on the car and `model` missing on the animal, both at the right line and column.
- Volar's language server dedupes diagnostics; the tsserver plugin path does not, so an error in a body used twice may show twice in an editor that uses the plugin.
- Parts checked with an untyped template and a wrong field: GridList, Tree, NavigationTree, SelectValue `render`, CalendarGrid `cell`, DateInput `segment`, TokenInput `token`, Tree with `treeData` items all type the parameter. TableBody gets `{ id: Key }` only (it does not see the Table's items), so table.md keeps the annotation and says why.
- Instantiations in packages/ui (`npx brumate-tsc --noEmit --extendedDiagnostics`): 7,698,025 on main and on the branch, the same. No template in packages/ui is untyped, so the generated code there is unchanged.

## 2026-10-28, review fixes

- `inlineTemplates` counted a template's own parameter of the same name, and its reads, so `#template file(file)` never inlined and its parameter was `any`. A template whose parameter has the name is now skipped in the count. Test: `#template item(item)` with `{item}`. A template that calls itself in its body still counts that call and stays declared.
- The website typecheck did not include ui/demos (0 demo files in the program). website/tsconfig.json now includes `ui/demos`: 64 files, no errors.
- Editor: an inlined template now writes `const row = $$template;` with `row` mapped to the name in `#template row(...)`, and each use writes `$$use(row);` mapped to the name at the use, before the call. Inside the prop, a comma expression `($$use(row), async (a) => ...)` would keep the context type, but TypeScript does not treat a comma expression as context sensitive, so a generic call could fix `V` before the arrow is checked. A statement of its own avoids that.
- Checked with a script on the TypeScript 6 API and Volar's proxy language service (not committed): hover on `item=row` shows `const row: (...args: any[]) => Promise<$$Markup>`; hover on the parameter shows `a: Animal`; go to definition from the use goes to the template name; references and rename from the name or a use list the name and both uses. The same script showed each body error twice before dedupe and once after.
- typescript-plugin wraps Volar's service and passes `getSemanticDiagnostics` and `getSuggestionDiagnostics` through `dedupeDiagnostics` (new export of language-core). The plugin has no test harness, and a fake tsserver `info` did not load the .brm files, so the test of `dedupeDiagnostics` is in the language-server suite.
