# Outcome: has-context

## Built

- `$hasContext(Context)` in `brumate/signals` (`packages/brumate/src/runtime/signals.ts`), also in `MACROS` (`macros.ts`) and the unshared list of `shared-module.ts`. It returns a boolean that is fixed when the scope is made.
  - Server: `Context.has(context, scope)` in `runtime/server.ts`. It uses `findProvider`, the walk over the `parent` ids that `Context.consume` now shares. It is `true` for `ROUTE_KEY` and `NAVIGATION_KEY`.
  - Browser: `hasContext(context, scope)` in `runtime/client/context.ts`, exported from `runtime/client.ts` and mapped as the `has` helper in `codegen/markup.ts`. It uses `findProvider`, and is `true` for `ROUTE_KEY` and `NAVIGATION_KEY` (with routes on) and for any key in `globals`. The page state gains nothing.
- Accepted shapes (all at the top level of a script, all `const`):

```ts
const found = $hasContext(Field); // a boolean
const x = $hasContext(Level) ? $store(Level) : undefined;
const g = $hasContext(Field) ? $getContext(Field) : undefined;
const y = $hasContext(Field) ? $store(g.state) : undefined;
```

- The test is exactly one `$hasContext(C)` call, the read is `$store(...)` or `$getContext(...)`, and the else branch is the identifier `undefined`.
- The guard must name the same context as the source of the read. Guard and source are compared as source text, after `resolveStores` found the source: for `$store(g.state)` the source is the context of `g`, so the guard must be that context, written the same way.
- Without a provider the variable is `undefined`. Codegen emits `has(C, scope) ? consumeStore(...) : undefined` (and `consume(...)` for `$getContext`), so the server records no `z` read and the browser links nothing; resume calls neither `set` nor writes the slot.
- Compiler: `Declaration.guard` (the context node of the guard) and `Declaration.hasSource` (for the plain boolean) in `model.ts`. The guard is read in `declareVariable` (`analyze.ts`); the guard check is in `resolveStores`. `graph.ts`: a `hasSource` declaration is not live. `codegen/markup.ts`: `specialCall` and `emitContexts` unwrap the guarded form.
- BRM197, in `error-catalog.ts` and pinned in `test/error-codes.json`.
- `.changeset/has-context.md`: brumate, minor.
- Docs: `website/docs/context.md` ("Reading without a provider"); skill `references/signals.md` (table row and entry). Generated by `UPDATE_SKILL=1 npx vitest run test/skill.test.ts test/check-command.test.ts`: `website/docs/errors.md` and skill `references/errors.md` (the BRM197 entry only).
- Tests: fixtures `Has*.brm` and `has*.brm` in `packages/brumate/test/stores/render`; the `$hasContext` and `BRM197` blocks at the end of `test/stores/stores.test.ts`; one `brumate check` test in `test/check-command.test.ts`.

## Deviations

- `$hasContext` also works as the value of a plain `const` (`const found = $hasContext(Field)`), which the brief did not list; it is a static context declaration. Any other place for `$hasContext` (an expression, a template, a `let`) is BRM197.
- `$route` and `$navigation` count as provided, so `$hasContext` is `true` for both on the server and in the browser.
- Review fix: the typing. `toTypeScript` (`packages/brumate/src/check.ts`, `guardedKeys`) writes `field!.state` in the virtual code for `$hasContext(C) ? $store(field.state) : undefined`, so the documented shape passes `brumate-tsc` under strict with no `?.`. `packages/language-core` and `packages/tsc` source did not change; the new test is `packages/tsc/test/tsc.test.ts` with the fixture `fixture-has`: `$hasContext` is `boolean`, a guarded `$store(Level)` is `number | undefined`, and `field.state` has no error.
- BRM197 has one message for every wrong shape, because only that one code is reserved.

## Gotchas

- Messages and examples (the exact BRM197 message):

```
Keep the answer of $hasContext with "const name = $hasContext(Context)", or guard a read of the same context with "const name = $hasContext(Context) ? $store(Context) : undefined", with const and no other test
```

- Fails with BRM197:

```ts
let x = $hasContext(Ctx) ? $store(Ctx) : undefined;              // let
const x = $hasContext(Other) ? $store(Ctx) : undefined;          // guard on another context
const g = $getContext(Ctx);
const x = $hasContext(Other) ? $store(g.state) : undefined;      // same, through a key
const x = $hasContext(Ctx) ? $store(theme) : undefined;          // the read is not of the guarded context
const x = $hasContext(Ctx) ? $store(Ctx) : null;                 // else is not undefined
const x = $hasContext(Ctx) ? 1 : undefined;                      // not a $store or $getContext
const x = $hasContext(Ctx, Other);   const x = $hasContext();    // not one argument
const x = [$hasContext(Ctx)];                                    // not a const or a guard
const g = $hasContext(Ctx) ? $getContext(Ctx) : undefined;
const y = $store(g.state);                                       // g is guarded, the read is not
```

- For a guarded `$getContext` value `g`, `$store(g.state)` must be guarded too: an unguarded one is BRM197.
- The guard and the source are compared as written. A guard `$hasContext(Ns.Ctx)` does not match a source `Ns.Ctx` written another way. Use the same imported name.
- A reader may use `field?.bump()` in a handler for a guarded `field`. The slot of a guarded `$getContext` is `undefined` without a provider.
- A `#loading` chunk reader asks on its own scope; the answer matches the page because the provider scopes are on the page state.
- `UPDATE_SKILL=1` rewrites `website/docs/errors.md`, the skill's `errors.md` and `error-codes.json` (new codes only). Run it after any change to the catalog.
- Under full-suite load `render.test.ts` and `resume.test.ts` fail at file level and one differential test and one feature-flag test time out; each passes alone.

## Proposed learnings

- A context read that can miss is asked with `$hasContext` of the same context, not caught | a missing provider throws, and a guard is static, so the answer is the same on both sides | packages/brumate/src | yes (the `$hasContext` tests)
