# Log: browser-loading-fallback

## 2026-11-02

- Probe (roadmap rule), on feat/browser-async d6a415ee: `test/render/loadingHost.brm` (an `#if` that opens a `#loading` over `LoadUser.brm`, whose `$memo(loadUser(id))` the test settles). Before the change the branch shows `<p class="user"></p>` with no fallback and fills `ada` later; client mode compiled `#loading` as a plain block. The gap is as the brief says, and the boundary of the contract is enough to close it: no contract change for the probe page.
- Design question: which waits a browser-rendered `#loading` counts. `wait` and `fillSettled` already `join`. A memo that markup reads without `await` waits nowhere. Counting every pending slot would hold the fallback for memos that only effects read (rejected in the loading-reload debate, P2). Followed the server instead: the memos the server waits for where they are declared (`blockingMemos`) count after `setSlots` of their scope, and the memos a body reads from outside (`awaitedMemos`, what `emitLoading` awaits) count at the start of the body.
- `countLoads` cannot live in `setSlots`: `components.ts` would import `waits.ts`, which imports `setSlots` (import/no-cycle). It is its own export, so a build that does not call it drops it, and the `loading` flag turns it into a no-op in builds with memos but no browser `#loading`.
- Waits follow the value, as `fillSettled` does, not the slot. A slot-based wait needs an end node for `until`, and the order of `setSlots` after the markup leaves the instance slots empty when the body of the same component renders.
- First runtime version showed the body when a load failed (fault without `f`). The server keeps the fallback and sends the error to the `#catch`. Changed: `loading` sets `f`, keeps the fallback and drops the held scopes; `countLoads` reports a rejection with `fail` once per error and scope (shared with `fillSettled` as `failOnce`).
- Found: an async memo whose expression is a template literal or another "primitive" node with `await` inside (`$memo(\`Hi ${(await load()).name}\`)`) compiles to an async IIFE in the browser, but `settledMemos`skips it as a primitive, so a browser render writes the promise as empty text and nothing fills it. Probe`AsyncText.brm`showed`""`after the load settled. The same check is on origin/main (markup.ts:566). Not fixed here;`mayLoad`counts`async-memo` regardless.
- `#reveal`: a group per block in the same render (`$$b.reveal(order, collapsed)`), closed in a microtask so `backwards` and `together` know the last body. The order code hangs on the group (`t`), so a page with `#loading` and no `#reveal` drops it.

- Review round 1 (fresh reviewer, pr-review): checks pass. Should-fix: `#reveal` ordered only the blocks of the same render function, while the server orders those of the components it renders too (probe: two components with their own `#loading`, the second settles first and showed). Non-blocking: `reveal` emitted with no `#loading` inside; a block that a later update adds joins a closed group; a second rejection of a failed body is not reported. Fix: `reveal(order, collapsed, body)` renders its body as a block that renders where it is and sets a module group while it runs, as `within` sets the boundary; `loading` clears it for its own body and fallback. Emitted only when the children hold a `#loading`, a component or a dynamic tag. Late blocks render outside the body, so they are not ordered (documented). Test for the components case added.
