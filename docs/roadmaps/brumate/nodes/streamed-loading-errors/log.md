- Probe on main (test/render/streamedCatch*.brm, a memo that rejects after the shell): `#catch` inside the `#loading` body and `#try` around the block both leave the fallback in the page forever. The server logs the error; the stream gets only the record that settles the memo.
- Root cause 1 (inside): the deferred body of a `#loading` or `#defer` block waits for its memos with `const data = await ...` before any markup. A rejected memo throws there, outside the `#try` inside the body, so the whole body fails. Memos that the page waits for already use `awaitHeld` (`let data; try {...} catch {}`) and read in place with `$$b.read`; the memos of loading bodies did not. Fix: `bodyMemos` (scopes.ts) joins the lazy set, and `emitLoading` and `emitDefer` use `awaitHeld`.
- Root cause 2 (around): when the body render rejects, `render()` only logs and calls `skip`, so the browser never learns. The `#try` is outside the body, so the server cannot render the `#catch` into the body. Fix: the server sends a state record with `b-fail="<boundary>"` whose code is the error (`caught()`, so production sends the generic message and logs the real one). The core (`readRecord`) hands it to `failBoundary` (errors.ts). The body has no scopes to go up from, so it walks the block markers around the `<!--lN-->` comment, from the inside out, finds the first `#try` whose entry is in the module's `t` table (owner kind and anchor) and calls `catchInto`. With none it dispatches `brumate:error`, as `fail` does.
- A `#try` ships its `#catch` body to the browser only when its body has client code or a memo read (`tryCatchesClient`). A `#try` in a parent that wraps only a child component with a failing `#loading` has neither, so the child's error ends as `brumate:error`. Not changed (it would ship every `#catch` that wraps a component). Noted in the outcome.
- Cut stream, measured by the debate (opponent-load-test): Chromium fires no `DOMContentLoaded` and no `load` after a dropped document stream, so the page cannot tell. Chosen: after client navigation, `failPending` (navigate.ts) runs when the reader ends and turns every `<!--lN-->` boundary that is still in the page (not a `#defer`, which has a `template[b-defer]` before it) into a `b-fail` record with a stopped-loading error. A document load stays pending, documented. The same record path as the server failure, so one client function.
- Not done: the bots path (`inOrder`) still keeps the fallback of a body that fails; a crawler reads no scripts. The reader erroring (`read()` rejects) is not handled; navigation reports it as before.
- Tests: resume.test.ts "an error inside a streamed #loading body" (inside, around, none, ended stream; 5 fail on main), navigate.test.ts (stream ends before the body).
- Round 2 (coordinator): rebased on main (#373, #375; one conflict in codegen/server.ts). The server can render the `#catch` of any `#try` around a failed body: a `#try` registers its `#catch` body as a closure on the context, a boundary keeps the chain, and the failure renders the nearest one. This covers a parent `#try` around a child component, and the `inOrder` path (string replace of the block range). The client needs only `replaceTry`, so the `t`-table walk stayed only for the cut stream, where no server answers.
- A `#try` with no markers (no client code) had no anchor, so tries that hold a component or a `#loading` now get one. Size vs main: +0.8 kB raw, +0.3 kB gzip (first version: +0.5 kB, +0.2 kB).
