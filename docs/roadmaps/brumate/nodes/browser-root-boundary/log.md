# Log: browser-root-boundary

## 2026-11-02

- Probe on 01017a8e (origin/feat/browser-async): seven tests in a new describe, "a block outside every #loading that the browser renders", against `waitHost`, `waitRows` and new fixtures. All seven fail as expected: the old branch goes at once and the sibling shows before the user (fill in place), a new row shows an empty `<li>`, B, A, B loads twice (`[1, 1]`), the old `#key` body goes at once, the old cleanups run before the new script (`['cleanup a', 'script b', 'client b']`), and `getFeatures` has no `rootWait`.
- `$effect` never runs on mount, and the compiler drops an effect whose reads are all constant, so the order fixture uses `$client(..., 'load')`.
- Design: `hold(at, key, render, show)` in waits.ts on `bound`/`give`, one held body per block keyed by its start comment (`holds`, a WeakMap). Same key again keeps waiting; another key drops it; `release(at)` marks it stale when the block goes back to what it shows, and a later ask for the same key takes it back (no second load for B, A, B). `swap` captures the old children before the render, so the new body (same kinds for `#key`) is not destroyed with the old. `holdRow` gives a waiting row an empty `<!--i<row id>--><!--/i-->`.
- Sites: `branch`, `rekey` (and `retag`), `fill`, `offscreen` first show, `list` fallback, `list` new rows. Not done: `reset`, `catchInto` (errors.ts -> waits.ts makes an import cycle that oxlint rejects), late `children`, `content`, portal. They fill in place.
- The old body of a `#key` that reads the key is live during the hold and loads for the new key too (`[1, 2, 2]` with `WaitUser id=(k)`). Kept, documented; the fixture uses a fixed id.
- `countLoads` counts in the root boundary (`HAS_LOADING || HAS_ROOT_WAIT`), as the server waits for those memos. Six existing tests assumed fill in place for memos that load and changed to the hold (#419/#421 gap tests, the promise prop tests of streamed-memo-reads, two browser-await tests). Two of them use a memo that never settles, so the block never shows, as the server never sends it.
- `AwaitReadKid` (`await side;` of a rejecting memo) reported twice once a boundary counted it: `unreadMemo` and `countLoads` both called `fail`. Moved the once-per-error-and-scope map into errors.ts (`reportOnce`) and used it in both. The same double report happens inside a `#loading` on feat/browser-async (from browser-loading-fallback); not on main, which has no `countLoads`.
- `vite.test.ts` "runs a form posted twice once" failed once under the full run, passed 3 of 3 alone.
